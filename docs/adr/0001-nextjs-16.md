# ADR-0001: Uso de Next.js 16

**Estado:** Aceptado  
**Fecha:** 2026-05-26  
**Autores:** Equipo FlappyVaina

---

## Contexto

Necesitábamos un framework React con routing, SSR opcional y buena experiencia de desarrollo. Las opciones consideradas fueron Next.js (versión estable más reciente), Vite + React Router, y Remix.

El proyecto requiere:
- Carga dinámica de módulos pesados (Three.js, MediaPipe) solo en cliente.
- Rutas simples y predecibles para cada juego.
- Build optimizado para producción sin configuración compleja.
- Posibilidad futura de añadir API Routes cuando llegue el backend.

---

## Decisión

Usamos **Next.js 16.2.6** con App Router.

Todos los componentes de juego se cargan con `dynamic(() => import(...), { ssr: false })` para evitar que Three.js y MediaPipe intenten ejecutarse en servidor.

---

## Consecuencias

**Positivas:**
- Zero-config para routing, build y optimización de imágenes.
- App Router permite layouts anidados limpios.
- `dynamic` con `ssr: false` resuelve el problema de WebGL en servidor de forma declarativa.
- Fácil añadir API Routes en el futuro sin cambiar de framework.

**Negativas / Riesgos:**
- Next.js 16 tiene breaking changes respecto a versiones 14/15 documentadas en la mayoría de tutoriales y en el conocimiento de entrenamiento de LLMs. Cualquier IA o desarrollador nuevo debe leer `node_modules/next/dist/docs/` antes de modificar código.
- El App Router tiene comportamientos de caché y revalidación que pueden sorprender si se añaden Server Components sin entender el modelo de datos.
- Si el proyecto no necesita SSR ni API Routes, Vite habría sido más ligero. Se acepta el overhead a cambio de la hoja de ruta.

**Regla derivada:** Nunca importar Three.js, MediaPipe ni Matter.js fuera de un componente marcado con `"use client"` o cargado con `ssr: false`.
